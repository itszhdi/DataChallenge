# Freedom CQA — оценка качества диалогов

Прототип Conversation Quality Analytics для хакатона Freedom Broker. Система оценивает работу оператора контакт-центра по настраиваемому чек-листу с помощью LLM. Для каждого критерия она показывает ответ, балл, вес, объяснение и реплики-доказательства. Оценку можно оспорить: проверяющий принимает решение, итог пересчитывается.

| Участники | `{{ИМЯ_1 — роль}}`, `{{ИМЯ_2 — роль}}`, `{{ИМЯ_3 — роль}}` |

| Модель для сдачи | `{{НАЗВАНИЕ_МОДЕЛИ}}`, режим `{{local / external_api / hybrid}}` |
| Демо-видео / презентация | `{{ССЫЛКА}}` |

## Что умеет система

**Контур 1. Оценка**

- **Чек-лист настраивается в интерфейсе.** Можно добавлять и менять критерии, формулировки, вес, тип ответа (Да/Нет, шкала, грубая ошибка), доступность N/A и её условие, шкалу числового критерия. Каждое сохранение создаёт новую версию, старые остаются доступны. Начальная конфигурация взята из чек-листа организаторов (`backend/checklists/default_checklist.json`).
- **Импорт диалогов.** Диалоги загружаются из API организаторов по `group_id`, по полной ссылке или из JSON-файла. Исходные `conversation_id` и метки времени сохраняются. Грязные записи не ломают импорт: они нормализуются, а предупреждения показываются пользователю.
- **Оценка выбранного диалога, пакета или в авторежиме.** Работает очередь с прогрессом и ETA, поддерживается RU, KZ и EN. Реплики бота и системные события служат контекстом.
- **Результат по каждому критерию:** ответ, баллы, вес, объяснение, реплики-доказательства и цитата. Если действие пропущено, указывается проверенный участок. Для N/A объясняется причина. Показываются итог и результаты по секциям.
- **Грубые ошибки** отмечаются отдельным флагом и итог не обнуляют.
- **Звонки.** Транскрипт из датасета или собственное распознавание записи (настройка `call_transcript`). Встроенный плеер; ссылка на реплику перематывает запись к нужному фрагменту.

**Контур 2. Работа с результатом**

- **Карточка диалога.** Из списка открываются транскрипт и оценка. Ссылки `#N` в обосновании подсвечивают нужную реплику, а в звонке ещё и перематывают запись.
- **Апелляция.** Пользователь выбирает критерий, пишет комментарий и сохраняет обращение.
- **Решение проверяющего.** Проверяющий видит спорную оценку, комментарий и фрагмент диалога, затем подтверждает или меняет оценку с указанием причины. Итог пересчитывается без вызова модели. В карточке видны исходная оценка, решение и финальный результат.

**Дополнительно**

- **Общий отчёт для супервайзера:**
  - KPI, включая главную проблему — критерий с самым низким средним;
  - средние по критериям, сегменты по языку и каналу, распределение итогов, монитор рисков;
  - клик по графику фильтрует список проблемных диалогов.
- **Отчёт оператору:** удачные действия, ошибки и конкретные рекомендации.
- **Частичная переоценка при смене чек-листа:**
  - изменение веса — пересчёт без модели;
  - изменённый или новый критерий — модель переоценивает только его.
- **Два профиля модели** (облачная и локальная). Переключаются в настройках без перезапуска, в каждой оценке записано, какой моделью она сделана.
- **Интерфейс:** три языка (русский, казахский, английский), светлая и тёмная темы, адаптивная вёрстка.
- **Экспорт:** результаты в формате организаторов JSON 1.0 с проверкой перед сохранением.

## Быстрый старт

### Что нужно

| Компонент | Версия |
|---|---|
| Docker + Docker Compose | любой актуальный (рекомендуемый способ) |
| или Python + [uv](https://docs.astral.sh/uv/) | Python 3.15+ |
| Node.js | 20+ (нужен только для разработки фронтенда; готовый интерфейс уже собран) |
| LLM | ключ Gemini API **или** локальная модель в Ollama / LM Studio |

### 1. Настройка бэкенда

```bash
cd backend
cp .env.example .env
```

В `backend/.env` укажите:

- `DATASET_API_URL` — ссылка организаторов **без** `&group_id` в конце (бэкенд дописывает его сам);
- для облачной модели: `LLM_API_KEY`, `LLM_MODEL`;
- для локальной модели: `LOCAL_LLM_BASE_URL`, `LOCAL_LLM_MODEL` (см. раздел [Модели](#модели)).

Файл `.env` содержит секреты, в репозиторий он не попадает.

### 2. Запуск бэкенда

**Docker (рекомендуется):**

```bash
cd backend
make docker-up            # облачная модель или LM Studio
make docker-up-ollama     # локальная модель в Ollama на Linux (контейнер в сети хоста)
```

**Без Docker:**

```bash
cd backend
make install              # uv sync
make run                  # http://localhost:8000
```

Проверка: `curl localhost:8000/api/health` возвращает активный профиль и модель.

### 3. Интерфейс

**Вариант А — готовый файл, без Node и сервера.** Откройте двойным кликом `frontend/build/index.html`. Весь интерфейс собран в этот один файл: JS, CSS, шрифты, логотипы.

- Бэкенд на `localhost:8000` подхватывается автоматически.
- Бэкенд на другом адресе: `frontend/build/index.html?api=http://адрес:порт/api`.

**Вариант Б — режим разработки:**

```bash
cd frontend
npm install
npm run dev               # http://localhost:5173
```

Если API работает на другом адресе, скопируйте `frontend/.env.example` в `frontend/.env` и поменяйте `VITE_API_URL`.

### 4. Первые данные

В интерфейсе: «Диалоги» → «Импорт» → `group_id` = `DEV`. Из терминала то же самое делает `make import-dev`.

## Модели

Есть два профиля. Активный выбирается в «Настройках» или командами `make use-gemini` / `make use-local`. `make models` проверяет доступность обоих профилей.

| Профиль | Режим в выгрузке | Что это |
|---|---|---|
| `gemini` | `external_api` | Gemini API (или любой OpenAI-совместимый провайдер в `LLM_*`) |
| `local` | `local` | Ollama или LM Studio на этой же машине |

Если оценки сделаны разными профилями, в выгрузке указывается `hybrid` и перечисляются все модели.

### Локальная модель: Ollama

```bash
ollama pull qwen2.5:7b
# ! Без этого шага Ollama молча обрезает промпт до ~2k токенов: промпт оценки занимает ~9–11k
printf 'FROM qwen2.5:7b\nPARAMETER num_ctx 16384\n' > Modelfile
ollama create qwen2.5:7b-cqa -f Modelfile
```

В `backend/.env`:

```env
LOCAL_LLM_BASE_URL=http://localhost:11434/v1
LOCAL_LLM_MODEL=qwen2.5:7b-cqa
LOCAL_LLM_API_KEY=ollama
LOCAL_LLM_TIMEOUT_SEC=600
```

Запуск: `make docker-up-ollama`, затем в настройках выберите локальную модель. Ollama слушает только `127.0.0.1`, поэтому контейнеру нужна сеть хоста.

### Локальная модель: LM Studio

```bash
lms get qwen/qwen3.5-9b@q4_k_m
lms server start
lms load qwen/qwen3.5-9b --context-length 16384 --parallel 1
```

Настройки LM Studio даны в `backend/.env.example`. Обязательно задайте `LOCAL_LLM_REASONING_EFFORT=none`, иначе модель тратит тысячи токенов на рассуждения до ответа.

### Облачная модель: Gemini

Укажите `LLM_API_KEY` и `LLM_MODEL` в `backend/.env`. На бесплатном тарифе квота ограничена числом запросов в день, поэтому бэкенд пережидает лимит в минуту паузами, а при исчерпании дневной квоты сообщает об этом. Пауза между запросами задаётся в `LLM_MIN_INTERVAL_SEC` или в настройках интерфейса.

## Как пользоваться

1. **Диалоги** → «Импорт»: укажите `group_id`, ссылку или JSON-файл.
2. «Оценить неоценённые» — пакетная оценка в фоне с прогрессом. Кнопка «Оценить» в строке оценивает один диалог.
3. Откройте диалог. Для каждого критерия видны ответ, балл, вес, объяснение и ссылки `#N` на реплики. Клик по ссылке прокручивает транскрипт, а в звонке перематывает запись.
4. **Апелляция:** «Оспорить» у критерия → комментарий → сохранить.
5. **Решение:** в том же критерии проверяющий подтверждает или меняет оценку и пишет причину. Итог пересчитывается, исходная оценка остаётся видна.
6. **Настройки:**
   - чек-лист (критерии, веса, шкалы, N/A) с кнопкой «Применить к диалогам»;
   - профиль модели, источник транскрипта звонков;
   - порядок очереди, потоки, задержка;
   - автооценка после импорта, авторежим, `group_id` по умолчанию.
7. **Общий отчёт:** KPI, графики и проблемные диалоги. Клик по графику фильтрует список.

## Сдача результатов: `results/dev/results.json` и `results/prod/results.json`

Файлы строятся из уже готовых оценок, модель при этом не вызывается. Перед записью выгрузка проверяется. При блокирующих ошибках файл не пишется, а ошибки выводятся в ответе:

- повторяющиеся или чужие `conversation_id`;
- недопустимые значения критериев;
- `evidence_turns` вне транскрипта;
- `critical_flag` не совпадает с `critical`;
- `final_score` вне диапазона 0–100.

```bash
cd backend

# DEV: 60 чатов + 5 звонков
make submit DATASET=DEV TARGET=dev TEAM="{{НАЗВАНИЕ_КОМАНДЫ}}"

# Контрольный набор (за час до стоп-кода)
curl -s -X POST localhost:8000/api/datasets/import -H 'Content-Type: application/json' -d '{"group_id":"{{PROD_GROUP_ID}}"}'
make batch DATASET={{PROD_GROUP_ID}}
make job JOB=<id из ответа>        # дождаться окончания
make submit DATASET={{PROD_GROUP_ID}} TARGET=prod TEAM="{{НАЗВАНИЕ_КОМАНДЫ}}"

git add results/ && git commit -m "results: dev + prod" && git push
```

Импорт и пакетную оценку можно сделать и в интерфейсе. Формат выгрузки:

- коды критериев `contact`, `discovery`, `identification`, `consultation`, `empathy`, `dialogue`, `closure`, `critical`;
- `true` / `false` / `null` (N/A), шкала — число ступени;
- `evidence_turns` — номера реплик с 1 по исходному транскрипту;
- диалог, который не удалось оценить, попадает в файл со `status: "error"` и причиной, а не скрывается.

Для сдачи звонки лучше оценивать по транскрипту датасета (`call_transcript = original`): тогда номера реплик совпадают с API. Если звонок оценён по собственному распознаванию, проверка предупредит об этом.

## Как считается оценка

Главный принцип: **модель отвечает — код считает.** Модель отвечает на вопросы чек-листа: Да/Нет/N/A или ступень шкалы, объяснение, реплики-доказательства, проверенный участок. Баллы считает код (`backend/src/features/evaluation/scoring.py`), поэтому расчёт детерминирован и проверяем.

1. **Да/Нет:** «Да» — полный вес, «Нет» — 0.
2. **Шкала:** вес × ступень / верхняя ступень.
3. **N/A** засчитывается только там, где он разрешён и выполнено условие. Вес такого критерия пропорционально перераспределяется между применимыми, максимум всегда 100.
4. **Грубая ошибка** — отдельный флаг, баллов не даёт и итог не обнуляет.
5. **Итог** округляется до двух знаков (Decimal, ROUND_HALF_UP).
6. **Время первой реакции** (порог 3 минуты) считает код от подключения оператора, а не модель.

Если меняется только вес, итоги пересчитываются без модели. Решение по апелляции пересчитывает итог так же.

## Точность и стоимость

Сверка с ручной разметкой: `make golden` сравнивает ответы модели с `backend/tests/golden.csv` по каждому критерию.

| Модель | Режим | Совпадение с эталоном | Время на диалог | Стоимость одной оценки |
|---|---|---|---|---|
| `{{МОДЕЛЬ_1}}` | `{{local / external_api}}` | `{{XX}}%` | `{{~N с}}` | `{{$0 / ~$X}}` |
| `{{МОДЕЛЬ_2}}` | `{{local / external_api}}` | `{{XX}}%` | `{{~N с}}` | `{{$0 / ~$X}}` |

Как считается стоимость: чат требует 1 вызов модели. Звонок с собственным распознаванием требует 2 вызова: распознавание и оценку. Токены каждой оценки пишутся в `meta` и в лог. Если задать цены в `LLM_PRICES`, стоимость считается автоматически. `{{Пример: ~X тыс. входных + ~Y тыс. выходных токенов ≈ $Z за диалог}}`.

## Архитектура

```
DataChallenge/
├── backend/            FastAPI + SQLite, оценка, очередь, апелляции, аналитика, экспорт
│   ├── src/
│   │   ├── llm/        клиент LLM (профили, лимиты, разбор JSON) и промпт
│   │   └── features/   datasets, conversations, checklists, evaluation, appeals,
│   │                   analytics, export, settings, worker, transcription, audio
│   ├── checklists/     начальный чек-лист
│   ├── tests/          автотесты и эталон golden.csv
│   └── Makefile        все команды разработки и сдачи
├── frontend/           React + Vite + Tailwind
│   ├── src/            страницы: общий отчёт, диалоги, карточка диалога, настройки
│   └── build/index.html  готовый интерфейс одним файлом
└── results/            dev/results.json, prod/results.json
```

- **Бэкенд:**
  - Python, FastAPI, uv, SQLite, Docker;
  - LLM подключается через OpenAI-совместимый API: Gemini, Ollama, LM Studio;
  - запросы к API организаторов и записи звонков идут через бэкенд, поэтому CORS не мешает.
- **Фронтенд:**
  - React 19, Vite, Tailwind CSS 4;
  - TanStack Query и Table, Recharts, Radix UI, i18next.
- **Хранение:** все оценки, версии чек-листа, апелляции и настройки хранятся в SQLite на бэкенде. В браузере остаются только язык, тема и выбранный набор.

### Адаптация под Dynamics 365

Интерфейс собирается в один HTML-файл без внешних зависимостей, поэтому его можно загрузить как HTML веб-ресурс Dynamics 365. Адрес API передаётся при открытии, пересобирать файл не нужно:

- параметр `?api=https://…/api` в ссылке на веб-ресурс;
- или `window.CQA_CONFIG = { apiUrl: 'https://…/api' }` до загрузки страницы.

Домен организации Dynamics добавляется в `CORS_ORIGINS` бэкенда. Маршрутизация работает через `#`, относительные пути (`base: './'`) позволяют открывать файл из любого пути.

### Пересборка интерфейса

После любых изменений в `frontend/src`:

```bash
cd frontend
npm run build:static      # → frontend/build/index.html
git add frontend/build/index.html
```

Файл сам не обновляется: если не пересобрать его, в репозитории останется старая версия интерфейса.

## Сценарий защиты на 5 минут

| Время | Что показываем |
|---|---|
| 1 мин | Общий отчёт → «Диалоги» → выбранный диалог `{{ID_ДИАЛОГА}}` |
| 2 мин | Оценка по критериям, обоснование, клик по `#N` → реплика (в звонке — перемотка записи). Пример N/A `{{ID_ДИАЛОГА_С_NA}}` и итоговый балл с перераспределением веса |
| 1 мин | «Оспорить» критерий → решение проверяющего с причиной → новый итог, исходная оценка видна рядом |
| 1 мин | «Настройки» → изменить критерий → сохранить новую версию → «Применить к диалогам»: модель переоценивает только изменённый критерий |

## Частые проблемы

| Симптом | Решение |
|---|---|
| Бэкенд не стартует, в логе `schema ... outdated` | Схема БД обновилась: `make clean-db && make run` (в Docker — пересоздать том), затем импортировать данные заново |
| Локальная модель отвечает ерундой или пустыми доказательствами | Модель Ollama создана без `num_ctx 16384`, и промпт обрезается — см. раздел про Ollama |
| Контейнер не видит Ollama | Запускайте `make docker-up-ollama` |
| «Дневная квота исчерпана» у Gemini | Переключитесь на другую модель (`LLM_MODEL`) или на профиль `local` |
| Интерфейс не видит API | Проверьте адрес (`?api=…`) и `CORS_ORIGINS` в `backend/.env` |
| После обновления страница выдаёт ошибку загрузки | Интерфейс перезагрузится сам; если нет — обновите страницу |
