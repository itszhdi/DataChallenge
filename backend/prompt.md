# Задача: бэкенд системы оценки качества диалогов (CQA) на Python + FastAPI

Ты пишешь бэкенд для хакатона Freedom Broker «Conversation Quality Analytics». Работай поэтапно (план в конце), после каждого этапа запускай тесты. Сначала всё должно работать в режиме `LLM_PROVIDER=mock` (без модели), потом подключаем Gemini.

## 1. Контекст задачи

Система оценивает работу ОПЕРАТОРА контакт-центра в диалоге с клиентом по настраиваемому чек-листу:

- **Контур 1 — оценка:** пользователь настраивает чек-лист (добавляет/меняет критерии, формулировки, вес, тип ответа, доступность N/A, шкалу), загружает диалоги и запускает оценку. Для каждого критерия система показывает ответ, баллы, вес, объяснение и реплику-доказательство. Если действие пропущено — указывает проверенный участок разговора. При N/A — объясняет причину. Показывает итог и результаты по секциям. Грубые ошибки отмечаются отдельно.
- **Контур 2 — апелляции:** пользователь открывает карточку (транскрипт + результат; ссылка в обосновании ведёт к нужной реплике или фрагменту звонка), оспаривает критерий с комментарием. Проверяющий видит спорную оценку, комментарий и фрагмент диалога, подтверждает или меняет оценку с причиной. Система пересчитывает итог. В карточке доступны исходная оценка, решение и финальный результат.
- **Контроль организаторов:** за 1 час до финала выдадут новый набор диалогов (другой `group_id`) — его нужно импортировать и оценить пакетно. На защите попросят **заменить один критерий** через интерфейс и применить новый чек-лист к диалогам.
- Авторизация не нужна. Подача апелляции и её рассмотрение — отдельные действия (роли без логина).
- Фронтенд (HTML/CSS/JS, совместимый с HTML-компонентом Dynamics 365) пишется отдельно и ходит в этот API. Нужен CORS.
- Для платной модели нужно уметь назвать стоимость одной оценки — логируй токены каждого вызова.

## 2. Стек и окружение

- Python 3.12+, FastAPI, uvicorn, pydantic v2, httpx, `openai` SDK (для Gemini через OpenAI-совместимый endpoint), pytest.
- База: **SQLite** через стандартный `sqlite3` (без ORM). Весь доступ к БД — только в модуле `db.py`, чтобы потом можно было заменить на PostgreSQL.
- Конфигурация через `.env` (+ `.env.example` в репозитории; `.env` и `*.sqlite3` в `.gitignore`).
- ОС разработчика: Arch Linux.

## 3. Формат данных организаторов

`GET <DATASET_API_URL>&group_id=DEV` возвращает:

```json
{ "error": "", "isSuccess": true, "data": {
  "dataset_group_id": "DEV", "total_records": 65,
  "records": [{
    "conversation_id": "p1-ru-001",
    "channel": "agent chat",
    "language": "RU",
    "transcript": [{"timestamp": "00:02", "speaker": "operator", "text": "Здравствуйте!"}],
    "audio_url": null
  }]
}}
```

- `channel`: `agent chat` или `voice call`. `language`: `RU`, `KZ`, `EN`. DEV: 65 диалогов (60 синтетических чатов + 5 реальных звонков; 35 RU, 15 KZ, 15 EN).
- `transcript` — уже массив. Роли `speaker`: `client`, `operator`, `bot`, `system`. Реплики бота и системные события — контекст (системные сообщения могут быть доказательством, например «клиент идентифицирован», «чат закрыт»).
- Время: у чатов `MM:SS`, у звонков ISO 8601 с часовым поясом. **Сохраняй исходные метки как есть**, а для UI/расчётов вычисляй смещение в секундах от первой реплики.
- `audio_url` пустой у чатов, у звонков — ссылка на запись.
- **ВАЖНО:** `DATASET_API_URL` уже содержит query-параметры (`api-version`, `sp`, `sv`, `sig`). `group_id` нужно ДОПИСЫВАТЬ к строке (`&group_id=...`), а не передавать через `httpx.get(params=...)` — httpx в этом случае затирает существующие параметры, и подпись `sig` пропадает. Ссылка содержит секретную подпись — только в `.env`.
- Также нужен импорт из загружаемого JSON-файла того же формата (запасной вариант).

## 4. Главный архитектурный принцип

**Модель только отвечает на вопросы чек-листа. Баллы всегда считает детерминированный код.**

- В БД сохраняются ОТВЕТЫ модели по каждому критерию (`na`, `value`, `explanation`, `evidence_ids`, `checked_range`, `flags`), а не баллы.
- Баллы, перераспределение N/A, секции и итог вычисляются функцией `score_evaluation(checklist, answers)` при каждом запросе.
- Следствия:
  - смена **веса** → новая версия чек-листа → мгновенный пересчёт всех оценок **без вызова модели**;
  - решение по **апелляции** → пересчёт без модели;
  - смена **формулировки / шкалы / N/A / пояснения** критерия или **новый** критерий → модель переоценивает **только эти критерии**, остальные ответы копируются.

## 5. Чек-лист (начальная конфигурация — положи в `checklists/default_checklist.json` и засей в БД при первом запуске)

Секции: `start` «Начало и понимание запроса», `safety` «Безопасность и решение», `flow` «Ведение и завершение диалога», `gross` «Грубые нарушения».

Формат критерия:
```json
{"id": "c04_consult", "section": "safety", "title": "...", "type": "binary | scale | flag",
 "weight": 20, "na_allowed": true, "na_condition": "...", "rule": "...",
 "scale": [{"value": 20, "description": "..."}],
 "guidance": "пояснение для модели", "examples_pass": [], "examples_fail": [], "flag_types": []}
```

Критерии (текст правил — дословно из чек-листа организаторов):

1. `c01_contact` «Установление контакта» — binary, вес 10, N/A нельзя. Правило: «Да — оператор поздоровался на языке клиента и представился в первом ответе.» Guidance: смотри первую реплику ОПЕРАТОРА, приветствие бота не засчитывается; язык приветствия должен совпадать с языком клиента; нужны и приветствие, и представление.
2. `c02_needs` «Выявление потребности» — binary, вес 15, N/A можно. Правило: «Да — оператор учёл известные детали и уточнил недостающее до ответа.» N/A: «Данных для ответа хватало с самого начала.» Guidance: «Нет» — если переспросил уже сообщённое клиентом (в т.ч. боту) или ответил, не уточнив недостающее.
3. `c03_ident` «Идентификация» — binary, вес 20, N/A можно. Правило: «Да — проверка личности подтверждена до раскрытия данных или защищённого действия.» N/A: «Запрос не требовал идентификации.» Guidance: подтверждение может быть в системном сообщении; общий вопрос о тарифах не требует идентификации (N/A); если проверка требовалась перед защищённым действием и не подтверждена в чате — «Нет».
4. `c04_consult` «Корректная и полная консультация» — scale, вес 20, N/A можно. N/A: «Чат закончился до того, как клиент сформулировал запрос.» Шкала: 20 — все существенные вопросы закрыты или дан корректный следующий шаг; 15 — основной вопрос решён, пропущена второстепенная деталь; 10 — часть запроса закрыта, существенный вопрос остался открытым; 5 — есть общая подсказка, но клиенту всё ещё непонятно, как действовать; 0 — ответа по существу нет или ключевая рекомендация ошибочна. Guidance: оценивается правильность и полнота решения, НЕ стиль общения.
5. `c05_empathy` «Эмпатия и клиентоориентированность» — binary, вес 15, N/A нельзя. Правило: «Да — оператор вежлив и, если клиент выразил недовольство или описал неудобство, отреагировал на конкретную проблему.»
6. `c06_flow` «Управление диалогом, скорость и грамотность» — scale, вес 15, N/A нельзя. Шкала: 10 — ответы ясные и связные, если было явное ожидание — оператор предупредил; 7 — один заметный сбой, но клиент может понять ответ и продолжить; 4 — клиенту приходится переспрашивать из-за формулировок или порядка ответов; 0 — из-за бессвязных или противоречивых реплик ход диалога непонятен. Guidance: порог первой реакции — 3 минуты (используй вычисленные факты о времени); оценивается понятность и последовательность общения, а не правильность ответа.
7. `c07_closing` «Завершение» — binary, вес 5, N/A можно. Правило: «Да — оператор подвёл итог или предложил дальнейшую помощь и попрощался.» N/A: «Чат оборвался до возможности его завершить.» Guidance: основание — последняя реплика оператора и системное сообщение о закрытии чата.
8. `c08_gross` «Грубые ошибки» — flag, вес 0 (без баллов), N/A нельзя. Правило: «Да — выявлено оскорбление клиента, предложение платной услуги в обход компании или раскрытие конфиденциальной информации.» `flag_types`: `insult`, `bypass_offer`, `confidential_leak`. Guidance: обход компании — оператор предлагает перевести деньги ему лично для инвестирования или просит личный номер клиента для частной платной консультации; достаточно самого предложения.

Настройки чек-листа: `first_response_threshold_sec: 180`, `rounding: 2`, примечание «Теги и вложения в оценку не входят».

Памятка организаторов (учесть в промпте): «Нет» — действие было нужно, но пропущено или выполнено неправильно; N/A — критерий неприменим по условию. Обоснование ссылается на конкретную реплику или системное сообщение; для пропущенного действия — место, где оно ожидалось; для N/A — какое условие выполнено. Пример обоснования: «Завершение — Нет. После ответа на вопрос оператор закрыл чат без прощания. Основание — последняя реплика оператора и сообщение о закрытии чата».

## 6. Правила расчёта (scoring.py) — строго по чек-листу

1. N/A только там, где `na_allowed`; если модель поставила N/A там, где нельзя — считать «Нет» + предупреждение.
2. binary: «Да» = полный вес, «Нет» = 0. scale: значение должно быть одной из ступеней (иначе привести к ближайшей ступени + предупреждение); баллы = вес × значение / максимальная ступень (верхняя ступень даёт полный вес).
3. Критерии с N/A исключаются; итог = сумма баллов / сумма весов применимых критериев × 100 (максимум всегда 100). Для каждого критерия вернуть также `effective_weight` и `final_points` после перераспределения.
4. Округление итога до 2 знаков **ROUND_HALF_UP** через `Decimal` (не встроенный `round`). Если применимых критериев с весом > 0 нет — итог `null` («не рассчитывается»).
5. flag-критерии баллов не дают: отдельный блок `gross_errors: {detected, types, criteria}`.
6. Секции: баллы и максимум по каждой секции после перераспределения.
7. Критерий без ответа модели (`status: error`) — исключить и вернуть предупреждение «итог предварительный».

## 8. База данных (SQLite)

- `conversations(id TEXT PK, dataset, channel, language, audio_url, transcript JSON, imported_at)`

Подключение: новое соединение на операцию, `timeout=30`, короткие транзакции (пакетная оценка пишет из фоновых потоков).

## 9. LLM-часть

### Провайдеры (`LLM_PROVIDER` в .env)
- `gemini` — Google Gemini API через OpenAI-совместимый endpoint `https://generativelanguage.googleapis.com/v1beta/openai/`, `openai` SDK, ключ из AI Studio в `LLM_API_KEY`, модель в `LLM_MODEL` (например `gemini-3.6-flash`). Используем **бесплатный тариф**.
- `openai` — любой OpenAI-совместимый сервер (LM Studio `http://localhost:1234/v1`), `LLM_BASE_URL`.
- `mock` — без сети: детерминированные валидные ответы по схеме (максимальная ступень, «Да», флаг 0). Для разработки и тестов.

Общий интерфейс: `complete_json(messages, schema) -> (dict, meta)`.

### Особенности бесплатного Gemini
- Лимиты непредсказуемы (порядка 10 запросов/мин и ограниченное число в день). Нужно: `LLM_MIN_INTERVAL_SEC` (глобальный троттлинг между запросами, по умолчанию 7 для Gemini), `LLM_CONCURRENCY=1`, при 429 — повтор с нарастающей паузой (15, 30, 45… с), до 5 попыток.
- `LLM_REASONING_EFFORT=low` — передавать как `reasoning_effort` (меньше токенов и быстрее).
- `response_format={"type": "json_schema", "json_schema": {"name": "evaluation", "strict": true, "schema": ...}}`. Gemini поддерживает подмножество JSON Schema: перед отправкой **удалить `additionalProperties`** и **числовые `enum` заменить на `description`** («Одно из значений: 0, 5, 10, 15, 20») — допустимость значений всё равно проверяет наш код. Строковые enum оставить.
- На бесплатном тарифе Google использует запросы для улучшения своих продуктов. Поэтому `EXCLUDE_CHANNELS=voice call`: диалоги этих каналов (5 реальных звонков) НЕ отправлять в модель — понятная ошибка (HTTP 403 для одиночной оценки, пропуск с причиной в пакете).
- Стоимость: на бесплатном тарифе 0; таблица цен в config на случай платного (`$ за 1M токенов`).
- Ответ может прийти в ```json-обёртке — извлекать первый `{...}`.

### Промпт (собирается из чек-листа — ничего не хардкодить под 8 критериев)
- system: роль эксперта QA брокерской компании; оцениваются только действия оператора; бот и system — контекст, но системные сообщения могут быть доказательством; диалог на RU/KZ/EN, **объяснения всегда на русском, 1–2 предложения**; `evidence_ids` — только существующие номера реплик; при пропуске — `checked_range` («#2–#5») и чего не хватило; N/A только при выполненном условии неприменимости с объяснением; не додумывать; сначала доказательства, потом объяснение, потом оценка.
- user: канал и язык; блок чек-листа (по каждому критерию: id, название, как отвечать для его типа, ступени шкалы с описаниями, правило, условие N/A или «N/A не допускается», guidance, примеры); блок «Факты о времени» (вычисляет `timing.py`: первая реакция оператора на первую реплику клиента и превышен ли порог 180 с; паузы клиент→оператор больше порога); транскрипт с нумерацией: `[#3] 01:10 оператор: текст`.

### JSON-схема ответа
Объект с полем на каждый оцениваемый критерий (все `required`). Порядок полей внутри критерия: `evidence_ids` (array of int), `checked_range` (string), `explanation` (string), `na` (boolean — ТОЛЬКО если `na_allowed`), `value` (integer; binary/flag: 0|1; scale: ступени), `flags` (только для flag, string enum из `flag_types`).

### Валидация ответа (evaluator)
- `evidence_ids` вне диапазона — удалить + предупреждение.
- значение шкалы не из ступеней — предупреждение (scoring приведёт к ступени).
- «Нет» без `checked_range` и без доказательств — предупреждение.
- нет ответа по критерию — `status: error`.
- битый JSON / сетевая ошибка — повтор до `LLM_RETRIES` (по умолчанию 2).

### Переоценка при смене чек-листа
Отпечаток критерия = хэш полей, влияющих на ответ: `type, rule, na_allowed, na_condition, scale, guidance, examples_pass, examples_fail, flag_types` (вес и секция НЕ входят). `diff_checklists(old, new)` → `same | weight_only | changed | new | removed | needs_llm`. `reapply(evaluation_id)` копирует ответы `same + weight_only`, для `needs_llm` делает ОДИН вызов модели только по этим критериям, сохраняет новую оценку с `parent_id`.

### Апелляции
Финальные ответы = исходные ответы модели + решения `changed` по апелляциям (в порядке id). Карточка возвращает `original` (score по исходным ответам) и `final` (с решениями), список апелляций.

## 10. API (все пути с префиксом /api)

| Метод | Путь | Назначение |
|---|---|---|
| POST | /datasets/import `{"group_id":"DEV"}` | Импорт из API организаторов |
| POST | /datasets/upload (multipart file, `?dataset=`) | Импорт из JSON-файла |
| GET | /conversations?dataset= | Список: id, язык, канал, audio_url, id последней оценки, итог, флаг грубых ошибок, число открытых апелляций |
| GET | /conversations/{id} | Диалог + история оценок |
| GET | /checklists | Список версий |

| PATCH | /checklists/active/weights `{"weights":{"c01_contact":30},"reapply_all":true}` | Новая версия только с изменёнными весами + пересчёт всех последних оценок без модели |

## 12. Тесты (обязательно, pytest)

Расчёт по дефолтному чек-листу:
- всё «Да» и максимумы шкал → 100.00;
- пример: c01 Да, c02 N/A, c03 Да, c04=15, c05 Да, c06=7, c07 Нет, c08 Нет → набрано 70.5 из применимых 85 → **82.94**;
- тот же пример, вес c01 изменён на 30 → **86.19** (без вызова модели);
- тот же пример, апелляция меняет c04 на 20 → **88.82**;
- c03 N/A + c01 Нет → 87.50, effective_weight c01 = 12.5;
- N/A там, где запрещено → «Нет» + предупреждение;
- флаг грубой ошибки не влияет на итог, тип попадает в gross_errors;
- все критерии N/A → итог null;
- шкала 13 → ступень 15;
- ROUND_HALF_UP: случай 88.125 → 88.13.

Интеграционные (mock, TestClient, временная БД): загрузка файла → оценка → пакет → смена весов (пересчёт без LLM) → изменение формулировки одного критерия + добавление нового → `reapply` вызывает модель только для них → апелляция → решение → final_total пересчитан; `EXCLUDE_CHANNELS` блокирует звонки; `dataset_url()` сохраняет `sig` и дописывает `group_id`; `gemini_schema()` убирает `additionalProperties` и числовые enum.
