# В этом файле описаны основные правила разработки серверной части проекта, при разработке CLAUDE CODE обязан соблюдать все стандарты описанные здесь
Этот проект - это реализация кейса проблемы CQA от Freedom банк. Задача: Реализовать систему для проверки диалогов оператора с клиентом и разбора того, насколько правильно справился оператор. 
Главная задача — создать работающую систему, которая осмысленно анализирует диалоги, применяет заданный чек-лист и выдаёт логичные, обоснованные оценки.

## Stack
Backend : Python[FastAPI], uv
SQLAlchemy 2.0
Infra: Docker, docker-compose

## Architecture
Проект представляет из себя клиент-серверную монолитную архитектуру, с подвзякой к LLM, сначала используется API Gemini Free Tier, потом возможно локально запущу Gemma или Qwen, когда все остальное будет готово и останется только модель. 

## Coding Standarts
Здесь описаны главные рекомендации что Claude Code должен делать и как
- Все сложные команды или многоэтапные команды должны быть записаны в Makefile для удобства разрабокти, самому Claude Code тоже рекомендуется использовать команды оттуда а не их прямое написание
- При комментировании Claude Code должен придерживаться строгого стандарта комментариев: Не использовать многострочные комментарии, все комментарии делятся на : * - для описания методов ** - важные ! - критически опасно TODO - сделать позже ? - комментарий с вопросом и стандартные комментарии для языка Python. Нельзя использовать многострочные комментарии, в особенности комментарии покрытые сверху и снизу длинным тире. Не используй AI-Typical комментарии вроде: ==============Функция============. Комментируй только самые важные части приложения
- Swagger использовать не нужно
- Правило Логгирования: Используй логгирование в самых важных местах, особенно там где могут быть ошибки, особенно связанное с AI. Также через логи нужно отслеживать. Все логи без исключения должны логгироваться на английском языке
- Приложение должно быть ориентированно на решение кейса. Критерии принятия следующие: Главная задача — создать работающую систему, которая осмысленно анализирует диалоги, применяет заданный чек-лист и выдаёт логичные, обоснованные оценки. Главный критерий - точность AI-оценки диалогов. Будет сравнение с заранее подготовленными эталонными оценками. Помимо точности, будем учитывать:
1. Функциональность и уникальные возможности: дополнительные полезные функции, интересные технические решения и качество реализации.
2. Удобство использования: насколько понятен интерфейс и насколько удобно организован весь процесс оценки диалогов.
3. Корректность процесса: действительно ли система анализирует новые диалоги и применяет заданные критерии, а не воспроизводит заранее подготовленные результаты.
4. Разнообразие технических подходов: при формировании топ-50 постараемся сохранить представительство разных архитектур, в частности решений на локальных LLM и облачных AI-сервисах.
5. Важно: точность относительно Ground Truth будет главным ориентиром, но итоговый отбор не сводится к автоматическому рейтингу по одному числовому показателю. Решение будет приниматься с учётом совокупности перечисленных факторов.

## Tips
Здесь описаны второстепенные рекомендации, которые при наличии архитектурных причин можно не выполнять
- Использовать uvloop и httptools(обе зависимости уже установлены через uv)
- Использовать async for вместо while True нотацию
- Использовать HTTPX AsyncClient вместо TestClient
- Использовать Lifespan State вместо app.state
