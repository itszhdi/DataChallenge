# Изменения API для фронтенда

Этот файл — задание для отдельной доработки `frontend/`. Каждый блок можно отдать Claude Code целиком: «Внедри во frontend изменения из backend/changes.md, раздел N». Поля сверены с работающим API (ветка `data_and_conv_branch`).

**Порядок внедрения:** раздел 1 обязателен первым (меняется формат id), затем 3 → 4 (статусы и авторежим), 5 (экспорт), 2 и 6 — по желанию. Бэкенд обратно совместим: текущий фронт продолжает работать, просто не показывает новое.

**Общие правила**
- Все новые тексты ошибок приходят в `detail` (строка). 422 — ошибка данных или нельзя оценить, 502 — модель недоступна (текст причины в `detail`).
- Долгие операции (оценка звонка, распознавание) могут идти минуты: не ставить на fetch таймаут меньше 10 мин, показывать статус из `/api/queue`.

## 1. Внутренний id диалога = `НАБОР:исходный_id`

**Что изменилось в бэкенде**
- `GET /api/conversations`: поле `id` теперь имеет вид `DEV:p1-ru-001`. Новые поля: `source_id` (исходный id организаторов) и `seq` (порядок записи в наборе). Список отсортирован по `dataset, seq`.
- Все эндпоинты с `{conversation_id}` (`/conversations/{id}`, `/audio/{id}`, `/prompt/{id}`, `POST /evaluate`) принимают внутренний id. Исходный id тоже работает, если он встречается только в одном наборе.
- `GET /api/export`: `conversation_id` — исходный id, плюс новое поле `dataset`.
- `POST /api/datasets/import|upload`: в ответе новое поле `warnings` (вложения, неизвестные роли, пустые реплики, реплики без времени, пустые транскрипты, повторы id в файле).
- `POST /api/evaluate` возвращает **422**, если диалог нельзя оценить (пустой транскрипт или нет реплик оператора). В пакетной оценке такие диалоги попадают в `skipped`.
- В транскрипте могут встретиться: `speaker: "unknown"` вместе с `speaker_raw`, флаг `empty: true`, массив `attachments` (в `text` уже добавлен маркер `[вложение: …]`).

**Что сделать во фронте**
- Показывать пользователю `source_id`, а в запросах использовать `id`. Подставлять `id` в URL через `encodeURIComponent` (в нём есть `:`).
- После импорта показывать `warnings` (свернуть, если их больше 5).
- Обрабатывать 422 у «Оценить» как понятное сообщение, а не как ошибку бэкенда.
- В транскрипте отображать роль `unknown` как «неизвестная роль (speaker_raw)», пустые реплики — серым «(пусто)».

## 2. Пересчёт, порог и апелляции

**Что изменилось в бэкенде**
- В критерии появилось необязательное поле `uses_timing: bool`: критерий опирается на факты о времени (по умолчанию так только у `c06_flow`).
- Результат diff (`POST /api/checklists` → `diff`) получил поле `threshold_changed: bool`. Если порог `settings.first_response_threshold_sec` изменился, критерии с `uses_timing` попадают в `changed`/`needs_llm`.
- Изменение `title` критерия теперь считается изменением формулировки (`changed`, переспрашивается модель), а не `weight_only`.
- Апелляции переносятся на новую оценку при `reapply` и при повторном `POST /evaluate`:
  - открытые переезжают;
  - решённые копируются, если критерий не менялся;
  - если критерий менялся, создаётся новая **открытая** апелляция, к комментарию добавлена пометка «[Критерий изменён после решения … — пересмотрите апелляцию]».
- Ответ `POST /evaluations/{id}/reapply` → `reapply.appeals = {moved, copied, reopened}`.
- При повторной оценке `meta.previous_evaluation_id` указывает на предыдущую оценку. `parent_id` по-прежнему ставится только при переносе (reapply).

**Что сделать во фронте**
- В редакторе чек-листа: чекбокс «Использует время (порог первой реакции)» → `uses_timing`, поле «Порог первой реакции, сек» → `settings.first_response_threshold_sec`.
- В панели diff показывать «Порог изменён — переоценка: …», если `threshold_changed`.
- После reapply показать тост, если `reopened > 0`: «N апелляций переоткрыто — критерий изменён».
- В истории оценок можно подписывать «повторная оценка», если есть `meta.previous_evaluation_id`.

## 3. Настройки, выбор модели, статусы анализа, ETA, Retry

**Новые эндпоинты**
- `GET /api/settings` → `{queue_sort, only_missing, include_errors, concurrency, request_delay_ms, auto_evaluate_on_import, default_group_id, auto_mode, auto_calls, auto_dataset, llm_profile, call_transcript, profiles: {gemini: {provider, model, base_url: null, active}, local: {provider, model, base_url, active}}}` (`auto_calls` — раздел 4, `call_transcript` — раздел 6).
- `PUT` и `PATCH /api/settings` — оба частичное обновление: любое подмножество полей:
  - `auto_mode: bool` — ручной или автоматический режим;
  - `queue_sort: "short_first" | "long_first" | "newest_first" | "oldest_first"` — число реплик или дата импорта; общий порядок для пакетной оценки и авто-воркера (после слияния заменил `auto_sort`);
  - `auto_dataset: string | null` — null означает все наборы;
  - `llm_profile: "gemini" | "local"` — применяется сразу, без рестарта.
  Неверное значение → 422.
- `GET /api/settings/models` — проверка профилей: `{gemini: {...}, local: {...}}`, у каждого `{model, available, model_loaded, models[]}`, а при недоступности `{model, available: false, error}`. Нужна для подсказки «LM Studio не запущен» (`available: false`) или «модель не загружена / неверное имя» (`model_loaded: false`: LM Studio в этом случае молча отвечает другой загруженной моделью).
- `GET /api/queue?dataset=` → `{model: {profile, name, avg_eval_sec, workers}, running: [...], queued: [...], upcoming: [...], failed: [...], counts: {...}, eta_total_sec}`:
  - в каждом элементе есть `conversation_id`, `source_id`, `dataset`, `source` (`manual|batch|auto`), `error`, `attempts`, `eta_sec`;
  - в `running` дополнительно есть `elapsed_sec`, в `queued`/`upcoming` — `position`;
  - `upcoming` — следующие диалоги авто-воркера (появятся в разделе 4).
- `GET /api/jobs?active=true` — задачи пакетной оценки (последние 20 или только активные): `{id, kind, status: running|finished, total, processed, model, done[], failed[], skipped[], created_at, finished_at}`. Нужен для восстановления прогресса пакета после F5. ! Задачи хранятся в памяти сервера: после рестарта список пуст. Статусы диалогов при этом не теряются, они в БД (`/api/conversations`, `/api/queue`).
- `POST /api/evaluate/batch` принимает `only_failed: true` — повтор только упавших (кнопка Retry). Диалоги, уже стоящие в очереди или в работе, повторно не ставятся.
- `GET /api/health` → `{status, profile, provider, model}`.

**Новые поля в `GET /api/conversations`**
- `status`: `null | queued | running | done | failed | skipped`.
- `status_source`, `status_error`, `status_attempts`, `status_queued_at`, `status_started_at`, `status_finished_at`.
- `eta_sec`: примерное время до конца для `queued`/`running`.
- После рестарта сервера диалоги, которые были `queued`/`running`, получают `failed` с ошибкой «сервер перезапущен во время анализа».
- Одиночный `POST /api/evaluate` тоже пишет статус (`source: manual`).

**Что сделать во фронте**
- Экран «Настройки»:
  - переключатель «Ручной / Автоматический» (`auto_mode`);
  - сортировка `queue_sort` (4 варианта) уже есть на вкладке «Очередь» — она общая для пакета и авторежима, отдельную не добавлять;
  - выбор набора (`auto_dataset`);
  - выбор модели Gemini/Локальная (`llm_profile`) рядом с результатом `GET /settings/models` (зелёный — доступна, красный — текст `error`).
- Список диалогов: в каждой строке бейдж статуса (в очереди №N / анализируется · ~Xс / ошибка / пропущен) и иконка ошибки с `status_error` во всплывающей подсказке. У `failed` кнопка «Повторить» → `POST /api/evaluate {conversation_id}`.
- Общий статус-бар над списком при `counts.running + counts.queued + counts.upcoming > 0`: «Анализ: X в работе, Y в очереди, ~Z мин (модель …)». При `counts.failed > 0` кнопка «Повторить упавшие (N)» → `POST /evaluate/batch {only_failed: true}`.
- Опрос `GET /api/queue` и `GET /api/conversations` каждые 2–3 с, пока есть running/queued или включён авторежим, иначе раз в 15–30 с.
- При загрузке страницы: `GET /api/jobs?active=true` → если есть задача, показать её прогресс (вместо хранения `R.job` в памяти). Состояние отдельных диалогов брать из `GET /api/queue` и полей `status*` в списке: они переживают и F5, и рестарт сервера.
- Если у ручного «Оценить» статус ответа ≠ 200, сразу показать ошибку в строке диалога (бэкенд уже записал `failed`).

## 4. Авто-воркер

**Что изменилось в бэкенде**
- Фоновый воркер живёт всё время работы сервера. При `auto_mode: true` он по одному берёт **неоценённые** диалоги без статуса:
  - фильтр `auto_dataset`;
  - сортировка `queue_sort`;
  - каналы из `EXCLUDE_CHANNELS` пропускаются.
- Упавшие (`failed`) и пропущенные (`skipped`) диалоги воркер **не повторяет**, нужен ручной Retry. Устаревшие оценки (после смены чек-листа) тоже не трогает, их переоценивают вручную.
- Пока идёт ручная пакетная оценка, воркер стоит на паузе.
- Новая настройка `auto_calls: "mixed" | "first" | "last"` (по умолчанию `mixed`) в `GET/PATCH /api/settings`: звонки (диалоги с `audio_url`) идут вперемешку с чатами, все сначала или все в конце. Внутри каждой группы порядок по-прежнему задаёт `queue_sort`. В `upcoming` у каждого элемента есть `is_call`, в `queue.worker` — `auto_calls`.
- `GET /api/worker` → `{alive, mode: manual|auto, status: idle|running|paused|error, reason, current, processed, failed, last_tick, last_error}`.
- `GET /api/queue` дополнительно содержит:
  - `worker` (то же, что и выше, плюс `auto_mode`, `queue_sort`, `auto_dataset`);
  - `upcoming` — очередь воркера в порядке обработки, с `position` и `eta_sec`.
- `eta_sec` в `GET /api/conversations` заполняется и для диалогов из `upcoming`.

**Что сделать во фронте**
- В статус-баре показывать состояние воркера:
  - «Автопроверка: анализирует SOURCE_ID»;
  - «на паузе — идёт пакетная оценка»;
  - «нет новых диалогов»;
  - «ручной режим»;
  - при `status=error` — `last_error` красным.
- Диалоги из `upcoming` помечать «в автоочереди №N · ~X мин», звонки (`is_call`) — иконкой телефона.
- В настройках авторежима рядом с сортировкой — выбор «Звонки: вперемешку / сначала / в конце» → `auto_calls`.
- Когда пользователь меняет сортировку, сразу перезапрашивать `/api/queue`: порядок `upcoming` пересчитывается.

## 5. Экспорт всех статусов и сохранение в results/

**Что изменилось в бэкенде**
- `GET /api/export` (schema_version `1.1`) содержит **все** диалоги набора, а не только оценённые. У каждого элемента есть `conversation_id` (исходный), `dataset`, `channel`, `language` и `status`:
  - `ok` / `partial` — есть оценка (+ `evaluation_id`, `model`, `criteria`, `score`);
  - `failed` / `skipped` — с `reason` (текст ошибки);
  - `excluded` — канал из `EXCLUDE_CHANNELS`;
  - `pending` — ещё не оценивался или в очереди.

  У неоценённых `criteria: []` и `score.final_score: null`. На верхнем уровне новые поля `dataset`, `generated_at`, `counts` (число по статусам).
- `GET /api/export?...&download=true` отдаёт тот же JSON с заголовком `Content-Disposition: attachment; filename="<DATASET>_<UTC-время>.json"`, и браузер скачивает файл сам.
- `POST /api/export/save?dataset=&team_name=&model_mode=&model_name=` сохраняет выгрузку в `results/` в корне проекта, файлы `<DATASET>_<UTC-время>.json` и `<DATASET>_latest.json`. Возвращает `{path, latest, file, counts, total, generated_at}`. Имя набора в имени файла очищается от небезопасных символов.

**Что сделать во фронте: две кнопки в блоке экспорта (вместо одной «Скачать оценки JSON»)**
1. **«Скачать отчёт»**: скачивание пользователю. Открыть ссылку `${backendUrl}/export?dataset=…&team_name=…&model_mode=…&model_name=…&download=true` (через `<a href download>` или `location.href`). Blob и `JSON.stringify` больше не нужны.
2. **«Сохранить на сервере (results/)»**: `POST ${backendUrl}/export/save` с теми же query-параметрами, затем тост «Сохранено: {file} · ok N · failed N · pending N» по `counts`.
- Обе кнопки используют текущий набор (`S.dataset`, пусто — все наборы) и поля «Команда / Режим / Модель». Проверка «укажите название команды» остаётся для обеих.
- Подсказка под кнопками: «В отчёт входят все диалоги набора, у неоценённых указан статус и причина».

## 6. Распознавание звонков (свой транскрипт через Gemini)

**Что изменилось в бэкенде**
- У диалога может быть свой транскрипт `transcript_asr` (распознан из `audio_url` моделью `TRANSCRIBE_MODEL`, по умолчанию `gemini-3.8-flash`) и `asr_meta` (`{model, seconds, audio_bytes, segments, tokens, created_at}`). Оригинальный `transcript` не меняется. Системные события («Запись запущена», «Клиент на удержании») переносятся из оригинала по времени и помечены `asr: false`, распознанные реплики — `asr: true`.
- Новая настройка `call_transcript: "asr" | "original"` (по умолчанию `asr`) в `GET/PATCH /api/settings`: по какому транскрипту оценивать звонки. Если у записи нет транскрипта в датасете, используется распознанный при любой настройке.
- При оценке звонка распознавание запускается автоматически, если своего транскрипта ещё нет. Это входит в статус `running`, поэтому оценка звонка длится несколько минут.
- `POST /api/conversations/{id}/transcribe` — распознать заново (принудительно).
- `GET /api/conversations/{id}` → `transcript_asr` (с `index`/`offset_sec`) и `asr_meta`. В списке новое поле `asr_messages` (null, если не распознан).
- Карточка оценки: `conversation.transcript` — **тот транскрипт, по которому оценивала модель** (номера `#N` совпадают с доказательствами). `conversation.transcript_source` равен `asr` или `original`. Снимок транскрипта хранится в оценке, в `meta` карточки его нет, а `conversation.transcript_asr` в карточку не попадает (он есть в `GET /conversations/{id}`).
- `EXCLUDE_CHANNELS` по умолчанию пустой: звонки теперь оцениваются.

**Что сделать во фронте**
- В карточке звонка бейдж «Транскрипт: распознан (модель) / из датасета» по `transcript_source`. На вкладке диалога переключатель «Распознанный / Оригинал» (если есть `transcript_asr`) и кнопка «Распознать заново» → `POST /conversations/{id}/transcribe` (долго: показывать спиннер, таймаут ≥ 10 мин).
- В настройках переключатель «Звонки оценивать по: своему распознаванию / транскрипту датасета» → `call_transcript`.
- Реплики с `asr: false` (системные из оригинала) стилизовать как системные события. Реплики с `pre_recording: true` (сказаны до события «Запись запущена», поэтому их нет в аудио и они взяты из транскрипта датасета) помечать значком «из датасета, до начала записи».
- Персональные данные в распознанном тексте маскируются так же, как в датасете: `[Персональные данные скрыты]`, `[Имя скрыто]`.
